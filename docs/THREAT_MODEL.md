# Threat model

## Protected assets

Execution authority, customer/operational data, tool credentials, agent prompts and external side effects.

## Trust boundaries

External HTTP input is untrusted. Model output is also untrusted: being generated by an approved model does not make it authorized. Tool/MCP/A2A responses are parsed as data rather than executable instructions.

## Controls demonstrated

- strict input contracts (`extra="forbid"`);
- no side effect before human approval;
- an atomic execution claim protects approval replay;
- retry policy excludes programming/contract errors;
- secrets are not required by the deterministic demo path;
- interoperability examples default to read-only/no-side-effect intent;
- CI separates deterministic authorization logic from variable model evaluation.

## Out of scope for the public lab

Enterprise identity, tenant isolation, secret rotation and network policy are deployment concerns and are intentionally not simulated here. They are documented rather than falsely represented by toy controls.
